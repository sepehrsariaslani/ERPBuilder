# Information hierarchy

Before layout, write the page job and answer: what happened, what matters, what next? This is the **Jobs/Purpose** test: the page should expose the essence of the user's task rather than mirror available fields. Put Level 1 glance data (identity, status, exception, next action) first; Level 2 operational data (items, amounts, owner, due date, relationships) in the main working surface; Level 3 advanced/system data (audit, IDs, technical settings) behind a labeled tab or disclosure. Required financial evidence remains one predictable step away.

Apply the **Ive/Rams** test before adding visual structure: understand why each piece exists, then remove or combine what is unnecessary. Simplicity is not an empty canvas. If an extra line of provenance, exception context, denominator, or next-step guidance reduces uncertainty, it makes the page simpler even though it adds content.

Build hierarchy with type roles, position, spacing, and alignment before adding borders, cards, badges, or color. Keep content first and reserve semantic color for real meaning. Dense accounting, POS, and stock views can show more Level 2 detail than overview pages. Remove a click, modal, or decoration only when the user's decision and recovery path remain clear.

Apply the **Raskin/Norman** test to attention: keep current mode, selection, totals, filters, and consequences visible when the user needs them. Do not make users remember hidden state from a prior screen. Group by the user's business mental model, not by backend table or API ownership.

Check the scan path with realistic Persian labels, long names, large numbers, exceptions, and empty values. Use wrapping or an intentional expansion path before truncating decision-critical data. A quiet product signature can live in typography, tone, or one useful interaction; repeating decorative cards, gradients, or oversized KPI numbers does not make a complex ERP easier to use.
